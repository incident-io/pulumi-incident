This repository bridges the incident.io Terraform provider (`incident-io/terraform-provider-incident`) into a Pulumi provider, using `pulumi/pulumi-terraform-bridge`. It exists for distribution: Pulumi can already drive our Terraform provider via `pulumi package add terraform-provider incident-io/incident`, but that generates an SDK on the user's machine and publishes no packages. This repo publishes pre-built SDKs to npm, PyPI and the Go module proxy.

Most changes do not belong here. Adding a resource, changing its inputs, or fixing its behaviour all happen upstream in `terraform-provider-incident`, and arrive here when the dependency is bumped. What lives here is the mapping layer: package names, per-language settings, and the CI that publishes the result.

See CONTRIBUTING.md, which covers the same ground for humans.

# Development guidelines

## What is hand-written vs generated

Hand-written, and the only files worth editing:

- `provider/resources.go`, the bridge configuration
- `provider/cmd/*/main.go` and `provider/pkg/version/version.go`
- `.ci-mgmt.yaml`, which generates the CI
- `mise.toml` at the repo root, for tool version overrides
- `.mk/incident.mk`, for local Makefile additions
- `.github/workflows/incident-*.yml`, the only workflows ci-mgmt does not own
- `README.md`, `CONTRIBUTING.md`, `docs/`, `examples/`, `.gitignore`

Generated, and overwritten by the build:

- `provider/cmd/pulumi-resource-incident/schema.json` and `bridge-metadata.json`
- everything under `sdk/`
- everything under `.github/workflows/` not prefixed `incident-`, plus `.config/`, `scripts/`, the `Makefile` and `.golangci.yml`

`schema.json` and `bridge-metadata.json` ARE committed, because the Pulumi Registry fetches `schema.json` from the repo at a release tag. Committed SDKs are what let consumers install a prebuilt package. Expect large mechanical diffs on every upstream bump; that is normal, and `.gitattributes` marks `sdk/` as generated so GitHub collapses it.

Anything carrying a `WARNING: This file is autogenerated` header loses your edits on the next regeneration. Change tool versions in the root `mise.toml`, which is not generated and takes precedence over `.config/mise.toml`.

## Building

```bash
mise trust
mise install
make build        # schema, provider binary, all three SDKs
```

If `mise activate` is not in your shell, prefix commands with `mise exec --`.

`tfgen` panics if the `pulumi` CLI is not on PATH, because it shells out to it to convert upstream's HCL doc examples into per-language ones. It does not degrade gracefully. The root `mise.toml` also provides the terraform converter plugin, which the generated Makefile cannot download for itself because it disables plugin acquisition.

## Verification

`make build` is expensive; it converts ~700 doc examples across 7 languages. The Makefile uses `.make/` stamp files so a repeat build is a no-op. Do not "fix" that by making targets phony.

After changing `resources.go`, run `make build` and inspect the `schema.json` diff. That diff is the real test of a mapping change.

`make test` runs the `examples/` programs through a real `pulumi up`, so it writes to whatever account the credentials point at. It needs both `PULUMI_ACC=1` and `INCIDENT_API_KEY`, and skips without either. Point it at a throwaway organisation, never a real one. The `PULUMI_ACC` gate exists so a key sitting in a shell is never enough on its own.

# Debugging

## Potential fixes for common issues

- **`bridge-metadata.json` replays past decisions, so changing an override in `resources.go` can silently do nothing.** `applyPrecomputedResourceFixups` replays what a previous tfgen run learned for each resource. If you change a `ResourceInfo` and regenerate, the stale decision can win with no warning. Reset the file to `{}` and regenerate to confirm what your change actually produces. This is not theoretical: it masked a real `ComputeID` fix until the file was reset.

- **Renaming a resource's `id` field disables the bridge's ID delegation.** Pulumi reserves `id` for the resource output id, so upstream resources that take `id` as an input get auto-renamed by the `fixID` fixup, which also sets `ComputeID` to delegate to the renamed field. Supplying `SchemaInfo{Name: ...}` yourself makes `fixID` bail early and skip that, and `fixMissingID` then hands every instance the literal id `"missing ID"`. If you rename an `id`, set `ComputeID: tfbridge.DelegateIDField(...)` alongside it. Check your work in `bridge-metadata.json`: a `"computeID": {"kind": "missing"}` entry on a resource that has a real identifier is the bug.

- **`TFProviderModuleVersion` must match upstream's major version.** The bridge uses it with `GitHubOrg` to find upstream's docs in the Go module cache. Get it wrong, including leaving it empty, and tfgen still succeeds; it just emits a schema with no docs and no examples. Watch the conversion rate tfgen prints, currently ~74%. A drop to 0% means the docs lookup broke. Bump this whenever upstream crosses a major version.

- **A failed lint leaves your working tree modified.** `make lint_provider` rewrites `//go:embed` to `// goembed` so the linter can run, then rewrites it back. The restore is a separate step, so a lint failure skips it and the files are left with a comment that no longer embeds anything. Fix with `git grep -l goembed -- provider | xargs perl -i -pe 's/ goembed/go:embed/g'`.

- **`make ci-mgmt` drops a trigger the release automation needs.** ci-mgmt generates `release.yml` with only a tag-push trigger, but `incident-sync.yml` tags with `github.token`, and GitHub refuses to start a workflow from a tag created that way. So `release.yml` carries a hand-added `workflow_dispatch` that regeneration removes. Use `make regen`, which runs the generator and then re-adds it. `incident-sync.yml` checks for the trigger before doing any work, so forgetting is loud rather than silent.

- **`.ci-mgmt.yaml` typos are hard errors that generate nothing.** The config is decoded with `KnownFields(true)`, so an unknown key aborts generation entirely rather than being ignored. Keys are inconsistently cased: `major-version` is kebab, `providerDefaultBranch` and `upstreamProviderOrg` are camel. Validate against `provider-ci/internal/pkg/config.go` rather than guessing, and run the generator to confirm.

- **Use `pulumi-labs/ci-mgmt`, never `pulumi/ci-mgmt`.** Upstream refuses non-Pulumi orgs, and does it by printing a redirect notice and returning exit 0, so it looks like a successful no-change run. It also hardcodes Pulumi's own ESC organization for OIDC, so its output cannot authenticate from this repo even if you bypass the org check. The fork lags Pulumi's version, which is why the root `mise.toml` pins newer Node, Python and golangci-lint than the generated config asks for.

- **ci-mgmt deletes workflows it does not recognise.** `clean-github-workflows` defaults to true and removes everything in `.github/workflows` whose name does not start with the provider name. Custom workflows must be called `incident-*.yml`.

- **`tfgen` does not rewrite `schema.json` when the content is unchanged**, so its mtime can end up older than the binary that produced it. Any Make dependency chain keying on `schema.json` directly rebuilds forever. This is why the schema step is stamped at `.make/schema`.

- **Do not add per-resource token mappings.** `tokens.SingleModule` plus `MakeStandard` maps all of them, and produces tokens identical to the dynamically bridged package already on the Pulumi Registry, which is what stops existing users' programs breaking. Manual tokens risk diverging from that.

## Releases

`incident-sync.yml` runs daily. When upstream has a newer release it bumps, regenerates, verifies, commits to master, tags mirroring upstream's bump type, and dispatches `release.yml`. It uses only `github.token`, with no PAT and no branch protection, following the same shape as `incident-io/sdk-go`.

It refuses two things and opens an issue instead of guessing: a major upstream bump, because that moves the Go module path and needs `resources.go` edited by hand, and a breaking schema change as judged by `schema-tools compare` against the last release.

ci-mgmt's own daily upstream-bump workflow is off (`checkUpstreamUpgrade: false`). It opens a separate PR per upstream release rather than maintaining one, and upstream ships often enough that they pile up when you only ever want the newest.
